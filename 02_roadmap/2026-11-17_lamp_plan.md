## Choices on ambiguities (binding for T2 to T12)

- C1. Kind words (A3, spec "move or export"): T2 moves the toast `words` map to `internal\waits\words.go`
  as `waits.KindWord(kind) (string, bool)`; `internal\toast\rules.go` reads it. Toast text stays byte
  for byte the same, proven by the unchanged toast tests. Lamp-only words (headlines, mood names, the
  lines) live in `internal\lamp\words.go` and `internal\lamp\lines.go`, because no repo words file exists.
  Reason: the spec asks for one table read by both; a full words file is outside the lane.
- C2. Time format (A2): new package `internal\timefmt` with `Short(sec int64) string` ("45 s" under 60 s,
  "12 min" under 60 min, "5 h" under 24 h, "19 d" from 24 h, all rounded down) and `Exact(sec int64) string`
  for the hover ("1 h 4 min 12 s", zero parts left out, "0 s" for 0). Used by the lamp only.
- C3. Who (vendor names): `internal\lamp\vendors.go` holds a Go copy of `HARNESS_LABEL`; a test reads
  `cmd\burnmon-dev\page.html` and fails when the two differ, so the fact keeps one rule (A4) without
  touching the page outside T6.
- C4. Counts (A4): the headline counts come from `wait_counts` when `lamp_foreman_items` is true; when it
  is false the lamp filters `wait_items` by kind only and counts per `group` field, never re-deriving a
  group. Rows always come from `wait_items` with their own `group`.
- C5. Read interval: `tick_seconds` of the last fresh snapshot; 2 seconds when there was none yet.
  Settings (`burnmon-dev.json`) and the theme (`burnmon-dev-view.json`) are read again every tick, so a
  change in the gear dialog shows without a restart of the lamp.
- C6. Settings live in `burnmon-dev.json` under the six `lamp_*` keys; `internal\lamp` parses them from
  the file bytes (a bad or missing value becomes the default); the lamp process finds the file through
  the same `devConfigReadPath` BurnMon Dev uses.
- C7. Single instance: Windows mutex `Local\burnmon-dev-lamp`. macOS: a flock on the data folder itself,
  opened read-only, so the lamp writes no lock file (spec item 5). The double-click "bring BurnMon Dev
  to the front" never calls `instance.AlreadyRunning(mutexName)` (that would take BurnMon Dev's mutex):
  it looks for the `BurnMon Dev` window with `instance.BringToFront`'s lookup and, when there is none,
  starts its own exe with no arguments through `os/exec`.
- C8. WebView2 profile of the lamp: `<settings dir>\wv2-lamp`, apart from `wv2-dev`, so the two processes
  never share a profile. The browser runtime's own cache there is not a BurnMon file; A6 (exactly one
  file, the ledger) is about files the lamp code writes. `--demo` uses a profile folder under
  `%TEMP%\burnmon-lamp-demo` instead, so the demo leaves nothing in a BurnMon folder; `--poses` and
  `--card` open no window and have no profile. The demo reads no settings and no theme file: it runs at
  `top-center`, dark theme, English, lines on. The demo test proves the demo code path writes nothing
  in a temp home.
- C9. Bindings: the lamp page calls only names with the prefix `lamp` (`lampState`, `lampNextLine`,
  `lampOpenDev`, `lampSize` and what T4 needs). Its list is `lampBindingNames` in
  `cmd\burnmon-dev\lamp_bindings.go`, checked with `winbind.PageCalls(lampHTML, "lamp")`. The 25 of
  `devBindingNames` stay untouched until T6 adds the gear binding.
- C10. Files (A7): `--poses` writes ten files (eight moods, `glim-sheet.svg`, `glim-demo.svg`). The spec
  test "writes nine files" is read as ten.
- C11. Demo timeline: eight segments of 3 seconds in the spec's order; inside `bored` the made-up wait
  grows so the wall shows 10, 15 and 20 bricks on its three seconds; the demo feeds 120 made-up burn
  samples so `sweating` can hold. One state per second, 24 states.
- C12. `glim-demo.svg` (X1): one SVG, 24 frame groups, each shown for one second with a CSS keyframe
  animation (`steps`), Glim drawn once per mood in `<defs>` and placed with `<use>` to stay under 200 KB.
- C13. Non-Windows: `lamp` on Linux and on darwin without cgo prints "The lamp runs on Windows only in
  this version." and exits 2 for every argument, `--poses` and `--card` included. The logic is one
  untagged function in `cmd\burnmon-dev\lamp_unsupported.go`, so the test runs on Windows.
- C14. Gear binding (T6): one binding `bdevSetLamp(key, value)` that accepts only the five gear keys and
  writes through `saveDevConfigKey`. `TestDevBindingNamesCoverPage` then expects 26; that is the "page
  tests that pin the gear dialog" exception.
- C15. The child (T6) lives in `cmd\burnmon-dev\lamp_child.go` behind a small starter seam in the style
  of `controls.Runner`; argv is exactly the own exe path and `lamp`.
- C16. uicheck (X5): the lamp process starts a uicheck eval server only with `BURNMON_LAMP_UICHECK=1`, on
  port 9336. The page exposes `lampRender(state)` and a freeze flag so the group sets a fixed state per
  mood and theme by eval only, with no `SendInput`. The group lives in `tools\uicheck\group_lamp.go`
  with its port and window lookup in `tools\uicheck\main.go`, in the way the Control Centre `gitpage`
  group does it; it does not join `devGroups`, so `tools\uicheck\groups.go`, its test and
  `scripts\uicheck.ps1` stay unchanged. Its runner is a new `scripts\uicheck-lamp.ps1` (pure ASCII, a
  product script, not scratch) that builds nothing, starts `burnmon-dev.exe lamp --demo` with
  `BURNMON_LAMP_UICHECK=1`, runs the group and stops the lamp.
- C17. T9 runs `.\scripts\uicheck-lamp.ps1` once. A red result caused by a locked screen or a missing
  desktop is a HAND line, not a FAIL of the code.
- C18. Ledger and card time: local time of the process; ISO week by Go's `time.ISOWeek`.
- C19. Build tags: `cmd\burnmon-dev\lamp_run.go` is `//go:build windows || (darwin && cgo)`, the tag of
  `main.go`, so the no-cgo darwin build never sees it. Per platform files hold what differs:
  `lamp_window_windows.go` (window, mutex, card window) and `lamp_window_darwin.go`
  (`//go:build darwin && cgo`). T5 writes the darwin file as a stub that prints the sentence of C13 and
  returns 2, so the `macos` check stays green from T5 on; T7 adds the card window stub to it; T8
  replaces the stub with the Mac lamp and the C7 flock. `TestDevBuildTags` pins every new file in the
  turn that makes it.
- C20. Documentation pins: when a new subcommand, config key or path turns `internal\doccheck` or a
  README test red in a turn before T9, that turn adds the shortest README line that makes it green, in
  `cmd\burnmon-dev\README.md`, inside its file budget. T9 then writes the full sections.
- C21. Repo paths in this plan are relative to C:\ZND\50_projects\burnmon, the repo root.
